# v0.19.3 mitigations + sandbox config audit

Expose the new agentsh v0.19.3 seccomp surface (`socket_rules`, `mitigation_sets`, `mitigation_dirs`) through the secure-sandbox TypeScript API, fill pre-existing gaps in `seccompDetails` and other sandbox config sections that surfaced during the audit, and enable the `dirtyfrag-conservative` mitigation by default in adapters that already ship seccomp defaults.

## Background

agentsh v0.19.3 ([#293](https://github.com/canyonroad/agentsh/pull/293), commit `f5315842`) adds three new fields under `sandbox.seccomp`:

| Field | Shape | Purpose |
|---|---|---|
| `socket_rules` | `[{name, family, type?, protocol?, action?}]` | Per-tuple `socket(2)`/`socketpair(2)` blocking. Finer-grained than the v0.19.0 `blocked_socket_families`. Action defaults to `errno`. Named `NETLINK_*` protocols are valid only with `family: AF_NETLINK`. |
| `mitigation_sets` | `string[]` | Named built-in mitigation IDs. Agentsh ships one today: `dirtyfrag-conservative` (Openwall Dirty Frag advisory, May 7 2026 — blocks `AF_RXRPC` and `AF_NETLINK`+`NETLINK_XFRM` with `log_and_kill`). Mitigations expand into `socket_rules` and family blocks server-side. |
| `mitigation_dirs` | `string[]` | Opt-in directories (inside the sandbox VM) holding `<id>.yaml` external mitigation files. Loading is deferred — only IDs referenced from `mitigation_sets` are read. |

v0.19.3 also rejects the removed `sandbox.seccomp.hardening_profiles` key with a hard error. secure-sandbox never wrote that key, so the rejection is a non-issue.

A broader audit of agentsh's full config schema (`internal/config/config.go`) against secure-sandbox's `ServerConfigOpts` (`src/core/config.ts`) revealed pre-existing gaps unrelated to v0.19.3:

- **seccomp:** missing `mode`, `unix_socket.{enabled, action}`, `syscalls.{default_action, block, allow, on_block}` (the syscall blocklist), and most `execve.*` sub-fields.
- **limits:** missing `max_disk_io_mbps`, `max_network_mbps`.
- **network:** only `intercept_mode` + `proxy_listen_addr` exposed today; missing `enabled`, `proxy_port`, `dns_port`, `tls_inspection`, `transparent`, `ebpf`, `rate_limits`.
- **fuse:** missing `audit.*` and `mount_base_dir`.
- **cgroups:** missing `base_path`.
- **unix_sockets:** missing `wrapper_bin`.

This spec includes the full audit fill. Operator/deployment knobs (auth, logging, audit storage/integrity/otel/watchtower, server transports, capabilities/landlock/security top-level toggles, MCP, XPC, mount profiles) are intentionally out of scope — they don't belong on a per-sandbox programmatic surface and would each warrant their own design.

## Goals

1. Map every agentsh seccomp YAML field 1:1 to a TypeScript field on `seccompDetails` (camelCase). Same pattern as the existing `blockedSocketFamilies`.
2. Map the broader sandbox-level gaps (`limits`, `network`, `fuse`, `cgroups`, `unixSockets`) the same way.
3. Validate up front, in TS, before serializing — catch typos and structural mistakes locally rather than waiting for agentsh's YAML loader to reject the config 200ms after sandbox spinup.
4. Enable `dirtyfrag-conservative` by default in adapters that already ship `seccompDetails` defaults today (`sprites`, `freestyle`, `runloop`, `exe`). Other adapters are unchanged.
5. Provide one small ergonomic — a `KNOWN_MITIGATIONS` constant — so callers get autocomplete and a single point of update when agentsh ships more built-ins.
6. No breaking changes. `execve: boolean` keeps working; sub-fields land on a new optional `execveDetails` object.

## Non-goals

- No higher-level "profile" abstraction layered on top of `mitigationSets`. Agentsh already provides the profile concept; layering another one on top would be premature curation.
- No `customMitigations: [{id, yaml}]` provisioning helper that writes mitigation YAMLs into the sandbox VM. Real complexity (per-adapter file-write timing, ephemeral vs preinstalled image differences). Callers who want custom mitigations write the YAML themselves and pass `mitigationDirs` plus their own `adapter.writeFile`.
- No agentsh version bump. Already on v0.19.3.
- No exposure of operator-only knobs (auth, audit storage, capabilities, landlock top-level, etc.).
- No new e2e tests. The existing live-provisioning e2e suites already validate that emitted YAML is accepted by agentsh; new unit coverage is sufficient.
- No CHANGELOG file (the repo doesn't have one today).

## Architecture

All TypeScript-side work lives in two existing files plus one new one:

```
src/core/config.ts          ← extend ServerConfigOpts + generateServerConfig
src/core/config.test.ts     ← extend existing seccompDetails describe block
src/core/mitigations.ts     ← NEW — KNOWN_MITIGATIONS constant
src/adapters/sprites.ts     ← add mitigationSets default
src/adapters/freestyle.ts   ← add mitigationSets default
src/adapters/runloop.ts     ← add mitigationSets default
src/adapters/exe.ts         ← add mitigationSets default
src/adapters/adapters.test.ts ← assert defaults
src/index.ts                ← re-export KNOWN_MITIGATIONS
docs/api.md                 ← document new fields + dirtyfrag default
docs/SPEC-v2.md             ← add table rows for new fields
```

No changes to the policy schema (`src/policies/schema.ts`) or its serializer — these are all sandbox-config-side, not policy-side.

## TS schema additions

Additions to `ServerConfigOpts` in `src/core/config.ts`. Existing fields are unchanged.

```ts
seccompDetails?: {
  mode?: 'enforce' | 'audit' | 'disabled';

  execve?: boolean;                        // unchanged (back-compat)
  execveDetails?: {                        // NEW — additive sub-object
    maxArgc?: number;
    maxArgvBytes?: number;
    onTruncated?: 'deny' | 'allow' | 'approval';
    approvalTimeout?: string;              // duration string e.g. "30s"
    approvalTimeoutAction?: 'deny' | 'allow';
    internalBypass?: string[];
  };

  unixSocket?: { enabled?: boolean; action?: 'enforce' | 'audit' };

  syscalls?: {
    defaultAction?: 'allow' | 'block';
    block?: string[];
    allow?: string[];
    onBlock?: 'errno' | 'kill' | 'log' | 'log_and_kill';
  };

  fileMonitor?: { /* unchanged */ };
  blockedSocketFamilies?: /* unchanged */;

  socketRules?: Array<{
    name: string;
    family: string;
    type?: string;
    protocol?: string;
    action?: 'errno' | 'kill' | 'log' | 'log_and_kill';
  }>;
  mitigationSets?: string[];
  mitigationDirs?: string[];
};

sandboxLimits?: {
  maxMemoryMb?: number; maxCpuPercent?: number; maxProcesses?: number;
  maxDiskIoMbps?: number;
  maxNetworkMbps?: number;
};

fuse?: {
  enabled?: boolean; deferred?: boolean;
  deferredMarkerFile?: string; deferredEnableCommand?: string[];
  mountBaseDir?: string;
  audit?: {
    enabled?: boolean;
    mode?: 'monitor' | 'soft_block' | 'soft_delete' | 'strict';
    trashPath?: string; ttl?: string; quota?: string;
    strictOnAuditFailure?: boolean;
    maxEventQueue?: number;
    hashSmallFilesUnder?: string;
  };
};

networkIntercept?: {
  enabled?: boolean;
  proxyPort?: number;
  dnsPort?: number;
  interceptMode?: string;
  proxyListenAddr?: string;
  tlsInspection?: { enabled?: boolean; caCert?: string; caKey?: string };
  transparent?: { enabled?: boolean; subnetBase?: string };
  ebpf?: {
    enabled?: boolean; required?: boolean; resolveRdns?: boolean;
    enforce?: boolean; enforceWithoutDns?: boolean;
    mapAllowEntries?: number; mapDenyEntries?: number;
    mapLpmEntries?: number; mapLpmDenyEntries?: number; mapDefaultEntries?: number;
    dnsRefreshSeconds?: number; dnsMaxTtlSeconds?: number;
  };
  rateLimits?: {
    enabled?: boolean;
    globalRpm?: number; globalBurst?: number;
    perDomain?: Array<{ domain: string; rpm?: number; burst?: number }>;
  };
};

cgroups?: { enabled?: boolean; basePath?: string };

unixSockets?: { enabled?: boolean; wrapperBin?: string };
```

The name `networkIntercept` is retained for back-compat even though the field surface now extends beyond pure interception (rate limits, eBPF DNS refresh). Renaming would be breaking.

`execveDetails` lives alongside the existing `execve: boolean` rather than replacing it. Setting `execve: true` and `execveDetails: { maxArgc: 64 }` together emits `sandbox.seccomp.execve: { enabled: true, max_argc: 64 }`. Callers that only care about toggling enforcement keep the simple bool.

## Known mitigations constant

New file `src/core/mitigations.ts`:

```ts
export const KNOWN_MITIGATIONS = {
  dirtyfragConservative: 'dirtyfrag-conservative',
} as const;

export type KnownMitigation =
  typeof KNOWN_MITIGATIONS[keyof typeof KNOWN_MITIGATIONS];
```

Re-export from `src/index.ts` so consumers do `import { KNOWN_MITIGATIONS } from '@agentsh/secure-sandbox'`.

This file becomes the single point of update when agentsh ships new built-in mitigations. Adding a new entry is a one-line change.

## Serialization

Each new field is serialized in `generateServerConfig` (same file) using the existing `if (field !== undefined)` pattern that the current `blockedSocketFamilies` mapping uses (lines 324–329). camelCase → snake_case at every level. Optional sub-fields are omitted when undefined to keep the YAML clean.

The seccomp auto-enable gate (which sets `sandbox.seccomp.enabled: true` whenever any seccomp field is set) is updated to also trigger on `mode`, `unixSocket`, `syscalls`, `socketRules`, `mitigationSets`, `mitigationDirs`, and `execveDetails`.

## Validation

Hand-rolled checks in `generateServerConfig`, throwing `Error` with a clear message early — same style as the existing `SEMVER_RE` check in `src/adapters/freestyle.ts`. Zod is intentionally not introduced here; `core/config.ts` doesn't use it today and the validation surface is small.

| Rule | Where | Message shape |
|---|---|---|
| `mitigationDirs[i]` must start with `/` | iterate `mitigationDirs` | `seccompDetails.mitigationDirs[${i}]: must be an absolute path, got "${path}"` |
| `socketRules[i].name` must be unique within the array | dedup pass | `seccompDetails.socketRules[${i}].name: duplicate name "${name}"` |
| `socketRules[i].protocol` starting with `NETLINK_` requires `family === 'AF_NETLINK'` | per-rule check | `seccompDetails.socketRules[${i}].protocol: NETLINK_* is only valid with family AF_NETLINK` |
| `syscalls.defaultAction === 'allow'` requires `syscalls.block` to be a non-empty array | top-level check | `seccompDetails.syscalls: defaultAction "allow" requires non-empty block list` |

These mirror the validation agentsh does server-side, but fail fast in TS so callers get actionable errors before paying for sandbox provisioning.

Validation for the broader fields (network/fuse/limits) is intentionally minimal — TypeScript's type system already covers structural mistakes; the above rules cover semantic gotchas specific to the seccomp surface.

## Defaults

`mitigationSets: [KNOWN_MITIGATIONS.dirtyfragConservative]` is added to the existing `seccompDetails` block of these adapters:

| Adapter | Why it qualifies |
|---|---|
| `sprites.ts` | already sets `execve: true` + `fileMonitor.enabled: true` |
| `freestyle.ts` | already sets `execve: true` |
| `runloop.ts` | already sets `fileMonitor.enabled: true` |
| `exe.ts` | already sets `fileMonitor.enabled: true` (with ptrace alongside) |

Adapters that don't ship `seccompDetails` defaults (`e2b`, `daytona`, `cloudflare`, `vercel`, `blaxel`, `modal`) are not changed. They rely on agentsh's built-in family defaults; opting them into a `log_and_kill` mitigation without setting any other seccomp expectations would be a surprise.

The two targets the mitigation blocks (`AF_RXRPC` and `AF_NETLINK`+`NETLINK_XFRM`) have no meaningful legitimate use in agent workloads, so the blast radius for default-on is near zero. A caller hitting one of these rules will get a killed process plus a `seccomp_socket_rule_blocked` audit event — loud but informative. Override is `mitigationSets: []`.

## Testing

Unit only. No new e2e.

`src/core/config.test.ts` — extend the existing `seccompDetails` describe block with one test per new field group:

- `mode` emits `sandbox.seccomp.mode`
- `unixSocket` emits `sandbox.seccomp.unix_socket.{enabled, action}`
- `syscalls` round-trips `default_action`, `block`, `allow`, `on_block`
- `execveDetails` emits as nested `sandbox.seccomp.execve.{max_argc, ...}`, coexists with bare `execve: true` (back-compat verification)
- `socketRules` emits the array; optional `type`/`protocol` are omitted when undefined
- `mitigationSets` and `mitigationDirs` emit string arrays
- One test per validation rule (absolute path, unique names, NETLINK_*-only-with-AF_NETLINK, default_action=allow requires block)

Plus the same pattern (one test per field group, omission verified for unset fields) for `sandboxLimits.{maxDiskIoMbps, maxNetworkMbps}`, `fuse.audit.*`, `fuse.mountBaseDir`, `networkIntercept.{enabled, proxyPort, dnsPort, tlsInspection, transparent, ebpf, rateLimits}`, `cgroups.basePath`, `unixSockets.wrapperBin`.

`src/adapters/adapters.test.ts` — extend the `provider defaults` describe block with one assertion per affected adapter (`sprites`, `freestyle`, `runloop`, `exe`) confirming the default emits `sandbox.seccomp.mitigation_sets: ['dirtyfrag-conservative']`.

`src/core/mitigations.ts` is small enough that a dedicated test file is overkill; the adapter assertions cover it indirectly.

## Risks and trade-offs

- **Default-on `dirtyfrag-conservative` could break exotic agent workloads.** Mitigated: action is `log_and_kill`, so failures are loud and produce audit events; override is one line.
- **Schema surface grows substantially.** Mitigated: all additions are optional and back-compat. Existing callers see zero behavioral change.
- **`mitigationDirs` points inside the sandbox VM.** Callers who want custom mitigations need to write YAMLs into the VM themselves. Documented explicitly; not handled by the library in this revision.
- **`execveDetails` alongside `execve: boolean` is two paths to the same agentsh field.** Mitigated by back-compat constraints; documented in api.md. A future major version could collapse them.
- **Hand-rolled validation drift from agentsh's server-side rules.** Mitigated: keep validation narrow (only the four high-value semantic rules above) so the TS check is a fail-fast layer, not a full mirror. If agentsh tightens a rule, the worst case is server-side rejection — the existing failure mode.

## Out of scope (for follow-up)

- MCP config (`sandbox.mcp.*`) — large structured surface, deserves its own design.
- Top-level operator knobs (`security`, `landlock`, `capabilities`, `mountProfiles`, `auth`, `audit.{rotation, storage, integrity, otel, watchtower}`, `policySocket`, `skillcheck`, `llmStorage`, `policies.signing`, etc.).
- A `customMitigations: [{id, yaml}]` helper that writes mitigation YAMLs into the sandbox VM at provision time — needs per-adapter file-write timing logic.
- Collapsing `execve` + `execveDetails` into a single shape — breaking, hold for a major version.
- Renaming `networkIntercept` to `network` to reflect the wider field surface — also breaking.
